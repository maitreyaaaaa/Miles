# Authentication setup

Miles delegates sign-in and email-code delivery to Supabase Auth. The browser uses Supabase's public publishable key. The FastAPI server accepts only Supabase user access tokens and verifies their signature using the project's JWKS endpoint. It never receives a service-role key.

## Supabase project

1. Create a Supabase project and configure the Google provider with a Google OAuth web client. Add Supabase's displayed callback URL to the Google client's authorized redirect URIs.
2. In Supabase Auth URL configuration, allow only the Google and Email providers and add the exact frontend callbacks: `http://localhost:5173/auth/callback` and `https://your-frontend.example.com/auth/callback`.
3. Enable email sign-in and change the email sign-in template to show `{{ .Token }}` so users receive the six-digit OTP rather than a magic link. Set a short code lifetime (10 minutes or less) and retain Supabase's resend and abuse controls.
4. Use an asymmetric JWT signing key so Supabase publishes verification keys at `/auth/v1/.well-known/jwks.json`. The API rejects shared-secret signing algorithms.

Supabase documents the OTP flow as `signInWithOtp` followed by `verifyOtp` with type `email`; its default email template sends a link until it is changed to include the token. See [passwordless email sign-in](https://supabase.com/docs/guides/auth/auth-email-passwordless). The API verifies issuer, audience, expiration, role, subject, and signature using Supabase's public JWKS, as described in [Supabase JWT verification](https://supabase.com/docs/guides/auth/jwts).

## Environment

Set the backend variables in `Application/.env`:

```env
APP_ENV=production
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_JWT_AUDIENCE=authenticated
ALLOWED_ORIGINS=https://your-frontend.example.com
DATABASE_URL=postgresql://miles_runtime.project-ref:password@pooler-host:6543/postgres?sslmode=require
DATABASE_POOL_MAX_SIZE=8
```

Production requires `DATABASE_URL`; the API refuses to start with local JSON persistence. See [data storage setup](data-storage.md) for applying the schema and creating the restricted runtime login.

Set frontend build variables in `Application/frontend/.env.local` (or the frontend host's environment settings):

```env
VITE_BACKEND_URL=https://your-api.example.com
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=your-supabase-publishable-key
```

The frontend key is public by design. Never put a Supabase secret/service-role key in a `VITE_` variable. `ALLOWED_ORIGINS` must contain exact origins; wildcard Vercel/Railway origins are not accepted. Local defaults are available only outside production.

Before opening Google Drive import to public users, complete Google's verification for the requested `drive.readonly` restricted scope; Google may require a security assessment. Publish a real app homepage and privacy policy that accurately describe microphone audio, transcripts, uploaded documents, provider processing, retention, and report sharing. See Google's [Drive scope guidance](https://developers.google.com/workspace/drive/api/guides/api-specific-auth) and [OAuth app homepage requirements](https://support.google.com/cloud/answer/13807376?hl=en).

## Local setup

Copy `Application/.env.example` to `Application/.env` and `Application/frontend/.env.example` to `Application/frontend/.env.local`, then set the Supabase project values. Configure the exact `/auth/callback` frontend URL in the Supabase redirect allowlist. Without both frontend and backend Supabase settings, sign-in is unavailable and protected API routes return `503`.

## Data boundary

The API derives ownership only from the verified JWT subject. Context dossiers, completed debate reports, and meeting sessions are scoped to the owner. Live debate engines are kept in process memory only while connected, with a 50-session concurrency limit. A debrief's explicit share link remains a public read-only capability; its random ID is generated by the server, and creating that link requires ownership of the source report.

Existing JSON records without an owner are not assigned to the first user who signs in. They remain on disk but are inaccessible through owner-scoped routes until an operator verifies ownership and migrates them deliberately.

Production stores contexts, meeting sessions, and debrief reports in Supabase PostgreSQL. Local development without `DATABASE_URL` continues to use JSON. Active debate sessions and meeting coordinators remain process memory; deploy one backend process until shared live-session coordination is implemented. Legacy JSON records without a verified Supabase account are not assigned to anyone; the importer reports and refuses owner IDs absent from the target project's Auth users.

## Google Drive and Calendar access

Google app sign-in uses OpenID scopes through Supabase. It does not grant access to Drive or Calendar. The user connects either integration separately, and Miles requests only Drive read access or Calendar event access for that action. Google OAuth redirects to `/google-integration-callback`; set `GOOGLE_REDIRECT_URI` to the exact deployed frontend callback URL and register that URL with the Google OAuth client. The app keeps the returned short-lived access token in tab memory and never returns or stores a refresh token. Private Drive imports and real Calendar event creation are unavailable until the user connects the matching integration. Publicly shared Drive links and simulated Meet links remain available without that consent.
